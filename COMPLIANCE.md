# Compliance, privacy and responsible-use notes (PS3)

This is a design-level assessment prepared by the team, not legal advice. CN's counsel and DPO should review it before production use. The supplied data is synthetic.

## 1. Where the rules bite on a location system

| Rule | Risk in this system | What we did |
|---|---|---|
| **RBI Fair Practices Code** (conduct, no disclosure of the debt to third parties) | A wrong pin sends an agent to the wrong house; asking neighbours can disclose the debt | Low-confidence addresses are routed to *verify first*, not to a blind visit. Directions are navigation only and never mention the borrower or the debt. Field scripts must ask neighbours only for the landmark / house, never the reason for the visit. |
| **DPDP Act 2023 - purpose limitation** | Location data reused beyond collections | Pins, trails and directions are produced and used only for collections and written to collections systems only. The package has no export to marketing or analytics stores. |
| **DPDP - data minimisation & retention** | Raw GPS trails (about 29 points per visit) are more data than needed | `extract_evidence.py` reduces each trail to one point + role + uncertainty. Raw trails and photos can be deleted once extraction is verified (the synthetic bundle keeps them so the work is reproducible). Retention periods are set by the lender's policy. |
| **DPDP - access control** | Field-ops data leaking to other uses | Recommended role-based access: field managers see territory pins and quality; agents see only their assigned addresses (the offline pack is per territory); model internals and calibration sets are restricted to the data team. |
| **Agent GPS / employment-law and monitoring framework** | Using GPS to monitor staff beyond collections | GPS is used only during working hours and only as evidence about *where the address is*. The integrity checks (repeated stops, photo reuse, per-agent caps) down-weight evidence; they are **review prompts, not accusations or penalties**. Agents are told what is collected and why. |
| **"The system does not infer locations beyond what collections needs"** | Scope creep (e.g. home / work patterns, movement profiling) | We locate *addresses* the lender already holds. No profile of a person's movements is built; borrower GPS is never collected; no inference about relationships or habits. |
| **Explainability / auditability** | Opaque scores | Every pin carries `method_used`, `clues_used` and `reason_codes`; every radius is calibrated and its calibration set is documented; every number in the package is regenerated by one command with tests. |

## 2. Fairness and feedback loops

* Historical visits reflect which addresses the incumbent policy chose to visit. We evaluate on addresses without visits and on independent survey truth, report accuracy by town and precision tier, and recommend an exploration share so low-confidence areas keep receiving evidence.
* `NO_LOCALITY_IN_TEXT` addresses skew to certain lenders' KYC formats; they are never penalised: a low tier means *verify*, never *write off*, and PS2 is told the address is only hard to find.
* Low confidence must never lead to harsher treatment of the borrower; it changes how the *agent* finds the address.

## 3. Human oversight

* Tiers are advice. A supervisor can override; overrides are logged.
* `address not traceable` is never set automatically from a low tier.
* Calibration drift triggers a human review, not an automatic change of radii.

## 4. Limitations to disclose

* All data is synthetic; accuracy on real addresses is unproven until the pilot.
* Survey truth covers residences only; office and native-village addresses are unvalidated.
* Direction phrases in Hinglish / Kanglish need native-speaker review.
* Coordinate orientation (x east, y north) is an assumption.
* The official-test fold was seen during exploratory analysis in Tasks 1-2; use fresh blinded survey data for any final claim.
